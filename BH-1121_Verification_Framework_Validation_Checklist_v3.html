2 Naming Resolution Note

Source_Record_Id__c vs External_Id__c: The original BH-1121 proposal referred to a field named Source_Record_Id__c as the source-system key. The implementation uses External_Id__c for this purpose. This is an intentional and safe divergence — the reconciliation service uses this field only as an idempotency key for upsert operations; there are no cross-reference joins that depend on the name.

Last_Sync_At__c (new field): This field was not present in the original proposal schema table but was added per delivery spec as a first-class audit timestamp. It is stamped by the reconciliation service on all ingest paths and is included in all four permission sets. This is an architecturally sound addition consistent with the framework's append-only audit philosophy.

Source_Payload__c (implementation addition): Present in the framework schema (see CLAUDE.md) but not originally specified in the BH-1121 proposal body. Included as a required framework field — every verifiable object must carry it. No action required; FLS coverage already added in all permsets.

5 Known Gaps — Items NOT Implemented in This Delivery
1
Is_Verified__c sync trigger for UHN_Publication_Author__c not created. The checkbox field exists but no trigger or handler was built to bidirectionally sync Is_Verified__c with Verification_Status__c on this object. The existing AAR_ScholarlyOutput_VerificationSync.trigger provides the reference pattern but has not been cloned for UHN_Publication_Author__c. This field will remain out of sync until a future delivery adds the trigger.
2
getRecentChangeEvents() is not yet wired in the LWC. The Apex method exists on VerificationCardController.cls and is callable, but verificationCard.js does not invoke it and there is no audit trail panel rendered in the component HTML. A future delivery will need to add the UI panel and wire the @wire or imperative call in the LWC.
3
New field test coverage — stampLastSyncAt() not yet asserted in any test class. The helper is invoked on Cases A, 2, and 4 but no existing test method asserts that Last_Sync_At__c is populated after a reconciliation run. Test coverage for this method should be added before the next delivery cycle.
4
Last_Sync_At__c is intentionally NOT stamped on Case 3 (drift detected) or Case 1 (no-op hash match). This is by design — only genuine ingest paths (Cases A, 2, 4) should update the sync timestamp. No action required, but testers should be aware that a failed sync or a drift-detection pass will not update this field.
