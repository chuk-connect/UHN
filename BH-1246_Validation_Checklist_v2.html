Risk Log

RESOLVED (was Medium) — VR_Lock_After_Submit formula too broad
Prior formula: ISPICKVAL(PRIORVALUE(Status__c), 'Submitted') — blocked ANY edit to a submitted record, including Admin fixing the Evaluator lookup, correcting AAR_Record__c, or reopening the record by resetting Status to Draft.
Fixed formula: Adds OR(ISCHANGED(Rating__c), ISCHANGED(Strengths__c), ISCHANGED(Concerns__c), ISCHANGED(Recommendations__c)) so only the 4 content fields are locked post-submission.
Deployed: commit f871393 · 2026-06-02 · Tooling API confirms Active=true with updated error message in sandbox.
OPEN ACTION (future BH-1010) — AAR_Submission__c legacy evaluator fields
Fields Evaluator_Comments__c, Evaluator_Score__c, Evaluator_Recommendation__c remain on AAR_Submission__c. BH-1246 creates the canonical model on AAR_Evaluation__c. Decision to migrate/remove the Submission fields is deferred to BH-1010. Fields are still referenced by VR_Evaluator_Assessment_Status on AAR_Submission__c — removal would break that rule. No action taken here to avoid breaking live sandbox functionality.
OPEN ACTION (future) — Institute Director read-all-within-Institute sharing
BH-1246 security model specifies Institute Directors should read all evaluations within their Institute. OWD=Private means a sharing rule is required. Per BH-1010 Apr 2026 decision, this should use the same Account-scoped Experience Cloud sharing rule pattern used for AAR_Record__c. Not in scope for this story; deferred to BH-1000/1001 evaluator workflow stories.
OPEN ACTION (future) — Evaluate locking Evaluator__c and AAR_Record__c after Submit
Current VR_Lock_After_Submit intentionally does NOT lock Evaluator__c or AAR_Record__c to allow admin corrections. If the requirement tightens to fully immutable records post-submit, revisit and add those fields to the ISCHANGED OR clause.
